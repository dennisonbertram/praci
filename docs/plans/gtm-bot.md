## Summary

GTM is a sidebar page with a docked GTM agent, like Legal. A founder types one go-to-market goal in the agent's panel; the agent writes it into its scratchpad as a plan (research, drafts, posts, directory signups, one-off emails), and a server-owned hourly routine wakes it to work one ready item per wakeup over days. The page shows the goal, "N need you", a Plan | Calendar switch, the agent's own stats page, a Channels table and the plan in four groups (Needs you, In progress, Drafts for you, Done with proof links), with a preview per channel. Layout C is the default; the agent can rearrange the page below the header and Needs you by placing live GTM blocks in its own page (Design 9).

Nothing public leaves without the founder: a post or a signup is a parked item the founder approves on the page; a directory signup may be opened by the agent itself only after three founder approvals in that channel and at most five a day; posts (X, LinkedIn, Threads, Bluesky) are approved every time and scheduled through the app-owned `gtm_post` REST adapter; the first-party Zernio MCP connection remains read-only. Emails are approved every time and sent through the founder's Gmail with the Inbox composer's own send path. The agent gets browser tools in a run only while an approved signup is open, and `gtm_post` only while an approved post is open and REST posting capability is ready; the call must match the approved text, absolute time and one account exactly and consumes the approval once before network dispatch. The agent cannot delegate to other bots and can only read mail. Every completed post or signup has a live URL as proof. Reddit, Hacker News and Product Hunt end as drafts.

Not built: a new plan model, direct X API posting, a bot-owned inbox, a self-scheduling tool, chat cards, delegation, Zernio's generated tools, email scheduling, Google Calendar sync, a native mobile screen. Reasons are under "Design", "Review changes" and "Out of scope".

## User story

From the framing (2026-10-19):

- **Faster.** GTM grunt work (finding 40 directories, filling forms, drafting channel-specific posts) happens while the founder does something else.
- **Simpler.** One goal in, one visible plan out; the founder only answers approvals instead of re-prompting a chat every few hours.
- **Trustworthy.** Every "done" carries evidence, and nothing public goes out in a new channel without the founder approving the first few items.

Shipped experience: the founder opens GTM, types the goal; the plan appears on the page grouped by what needs them; over the next days the agent wakes itself, completes ready items and records proof; posts, signups and emails wait under "Needs you" with a preview of exactly what goes out; after three directory approvals the agent proceeds within a daily cap; Reddit/HN/Product Hunt tasks end as drafts; an item waiting on the founder stays parked while other items continue; nothing is silently cancelled.

Each slice below names the story point it serves.

## Design

### 1. The plan is the scratchpad

Each plan item is a `ScratchpadItem`. One additive migration adds nullable columns:

- `category`: `goal` | `research` | `draft` | `public_post` | `create_account` | `outbound_email`. Set at creation only. Null means a plain item; other bots are unchanged. At most one non-done `goal` item per bot; its title is the page header's goal.
- `channel`: `x` | `linkedin` | `threads` | `bluesky` | `reddit` | `hn` | `producthunt` | `directory` | `email`. The directory host lives in title, notes and proof, so three approvals in `directory` accumulate across sites.
- `target` (≤ 200 chars): Zernio account id for a post, site host for a signup, To address for an email.
- `scheduledFor`: when a post should publish (Zernio) or a signup should be worked. Part of what the founder approves.
- `proof` (≤ 2,000 chars): required to complete a `public_post` or `create_account` item and must contain an `http(s)` URL; for `outbound_email` the send reference.
- `approvedAt`, `approvedBy` (`user` | `policy`).

The item remains the plan, but mutable approval columns are not quota history. S1b adds `ScratchpadApproval`, indexed by space, user, bot, category, channel, approval source and time. Its `itemId` is a non-cascading value: edits, reparking, founder discard and normal scratchpad expiry cannot erase approvals. Space, user and bot cleanup retain cascading lifecycle semantics. There is no agent tool or RPC to edit/delete history. Why not the alternatives: `Ticket` is space-wide, behind a flag, and its wake runs are hidden; a new `PlanTask` model would duplicate the scratchpad's title, status, notes, tools and prompt injection.

### 2. One store invariant: a gated item is open only with `approvedAt`

`public_post`, `create_account` and `outbound_email` are gated. The store (`scratchpad-tools.ts`) enforces for every path:

- A gated item is created `parked`; `open` or `done` at creation is an error. Before `approvedAt` the agent may change `title`, `notes`, `target` and `scheduledFor`; after `approvedAt` all four are frozen for the agent. The founder's RPC is never bound by agent rules.
- A gated item may be `open` only with `approvedAt` set. The founder's path: Approve calls `scratchpad.update({ status: "open", updatedAt })` with the `updatedAt` the page rendered; a founder `open` on a gated item without `updatedAt` is rejected; the store runs one `updateMany where { id, spaceId, userId, status: "parked", approvedAt: null, updatedAt }` setting `approvedAt` and `approvedBy: "user"`; count 0 returns an `ORPCError` with code `CONFLICT` (the pattern at `router.ts` `mcp.servers.update`), and the page says "Changed, review again" and reloads the item.
- The agent's path on `create_account` in `directory` only (S1b): founder approvals and policy decisions share `pg_advisory_xact_lock` on `gtm-channel:<spaceId>:<userId>:<botId>:directory`. Reload/version-check the item inside the transaction, then conditionally open the unchanged parked, unapproved item and append its history in that same transaction. Failed/stale approvals, already-open retries and no-ops record nothing. An edit racing the conditional write cannot approve changed content.
- Directory threshold and cap read **only durable history**, scoped by space, user, bot, category and channel. At least `APPROVALS_BEFORE_AUTO` (3) **distinct items** with founder approvals in the rolling window establish eligibility; repeated founder approvals of one item count once. Every successful policy opening counts toward `AUTO_DAILY_CAP` (5), including later reopenings of the same item. Founder approvals are not constrained by this cap. The window is `(now - 24 hours, now]`: exactly 24-hour-old and future events are excluded; the current instant is included. Time is sampled after acquiring the lock, so a waiting request evaluates its own current window.
- The additive history migration conservatively backfills still-present `create_account`/`directory` rows in `open` or `done` with a non-null approval time and a recognized `user`/`policy` source. Cleared/deleted approvals and earlier reopenings cannot be reconstructed; permanent history applies from rollout onward, plus these recoverable approvals.
- `public_post` and `outbound_email` have no agent path: the agent's `parked` → `open` is always rejected.
- **Re-park un-approves, and never touches `proof`.** The agent's `open` → `parked` on a gated item clears `approvedAt` and `approvedBy` only and may add a note. The item then shows under Needs you marked "Changed" for re-approval. Only a definitive Zernio REST rejection may clear an execution stamp; the founder's explicit Re-approve clears an uncertain stamp only after checking Zernio's queue. HTTP 5xx, timeout, thrown calls, malformed or ambiguous responses, and missing required success proof keep the stamp because the write may have happened. A parked item that still carries a stamp shows "Posting may have failed" with Re-approve. A denied call, a past time, a CAPTCHA or a payment step comes back to the founder through re-park without losing any stamp.
- Agent proof writes go only forward: null or the server's stamp → `zernio:<postId>` → `http(s)` URL; never cleared by the agent, including by re-park. A `done` gated item is not reopened by the agent. The RPC `scratchpad.create` goes through the same store.

No chat card is involved, so no item pauses a run.

### 3. Run gates: browser and Zernio only while an approved item is open

For the GTM spawn key:

- `pageBrowserAllowed` (`executor.ts:4226`) is true only when an `open` `create_account` item with `approvedAt` set exists for (spaceId, userId, botId) at run start. `computer_*` is not in the tool set. Remaining risk, stated plainly: while any approved signup is open, that run's browser is unrestricted and page text can steer it; the gate bounds when the browser exists, not what it does.
- `gtm_post` is an app-owned built-in, never an MCP tool. S3c registers and exposes it only for an `open` `public_post` item with `approvedAt` set, no proof stamp, and `ready` Zernio REST capability. It always takes the mandatory approval-effect path, consumes the exact matching item before any network request, and never falls back to a card. MCP discovery remains a closed read-only list of nine known tools; there is no remote write or generated-tool route to expose.
- `request_takeover` is offered only on runs the founder started (`user`, `follow_up`), never on routine runs: a takeover is `waiting_takeover`, counted active by `wakeRoutine` (`executor.ts:3319-3331`) and cancelled at 24 h, so a CAPTCHA at night would block every other item and hold the founder's messages. On a routine run the agent re-parks the item with the step in `notes` and stops.

### 4. Wakeups are a server-owned routine

`ensureGtmAgent` creates one hourly routine per agent under `lockGtmBot` (`pg_advisory_xact_lock` on `gtm-bot:<botId>`), `notify: false`, named "Work the plan". Its prompt: work the one item named by id in the prompt (the oldest workable `open` item, chosen by `findWorkableOpenItem` at wakeup because the agent cannot list all items), record proof, complete it, stop. Inside the claim transaction beside the Legal branch (`executor.ts:3319`): skip when the routine already has an active run, and skip when no workable `open` item exists, where a `public_post` whose `proof` starts with `zernio:` and whose `scheduledFor` is in the future is not workable. An approved post whose `scheduledFor` is already past at wakeup is re-parked by the agent (Design 2) with a new proposed time. Cut: a self-scheduling tool.

### 5. Zernio: the opened item is the approval, and the call must match it

The GTM agent owns the Zernio MCP link for reads, like the Carta agent owns its link. Authenticated MCP `tools/list` metadata reports `posts_create` with required `content` and `platform`, optional `account_id`, `profile_id`, `is_draft`, `publish_now`, integer `schedule_minutes`, `media_urls` and `title`, and no absolute timestamp; that missing timestamp is why posting uses a separate app-owned REST path. The official [create-post](https://docs.zernio.com/posts/create-post) and [get-post](https://docs.zernio.com/posts/get-post) docs describe the REST request, Bearer API-key auth and proof fields. MCP auth is through the linked MCP connection; REST API-key auth is from the docs, not a live test. No provider request or real credential was used. An OAuth MCP token is never forwarded to the REST origin. S3a preserves OAuth MCP linking and reads while adding the existing generic API-key configuration path. No Zernio-specific environment variable or new credential store is introduced.

1. **Closed read allowlist.** `INTEGRATION_PRESETS.zernio.allowedTools` is exactly `accounts_list`, `accounts_get`, `profiles_list`, `profiles_get`, `posts_list`, `posts_get`, `posts_list_failed`, `media_check_upload_status`, and `docs_search`; `forcedWrites` is empty. `posts_create`, all other writes, generated tools, and the dispatchers `call_tool` and `search_tools` are never offered or run through MCP. The S4 API overview uses only `accounts_list`; Calendar queue reads use the app-owned REST adapter, never MCP `posts_list`. S2 adds only preset data; S3a owns the Zernio endpoint/key/`requiresAgent` branches. `assignmentAllowsTool` (`mcp-connector.ts:163-176`) enforces the closed list at discovery and immediately before every call (`:493`), whatever the stored row says.
2. **App-owned tool and capability.** `gtm_post` is registered as a local built-in and exposed only by S3c while an approved, open, unconsumed post is available and the actor's Zernio REST posting capability is `ready`. It is not part of `GTM_AGENT_BUILTIN_TOOLS` or the MCP preset. S2 adds contracts and preset data only; it does not touch `packages/contracts/src/builtin-tools.ts` or `packages/adapters/src/builtin-tools.ts`, which S3c owns for tool definition and registration. The UI/API distinguish `not_connected`, `api_key_required`, and `ready`.
3. **Match, consume, then dispatch.** `gtm_post` accepts only the strict input `{ content, scheduledFor, accountId }`; `scheduledFor` is absolute ISO 8601 with a UTC/offset, `accountId` is one string, and unknown keys are rejected. Platform comes from the approved item's channel (`x` → `twitter`); the caller cannot override it. On the mandatory approval-effect path, regardless of saved rules, Auto Review or "Always allow", the executor checks exact text, exact instant, exact account and `scheduledFor` at least ten minutes ahead, then atomically consumes the matching item before any network call. A mismatch is denied before the effect or request; concurrent calls cannot consume the same approval. Only the REST adapter sends `POST https://zernio.com/api/v1/posts` with Bearer API-key auth and exactly `{ content, scheduledFor, platforms: [{ platform, accountId }] }` for one platform/account. It sends no `publishNow`, `isDraft`, media, title, or other override. OAuth MCP tokens are never forwarded across origins.
4. **Outcomes and proof.** A definitive provider rejection may clear the stamp. HTTP 5xx, timeout, thrown calls, malformed or ambiguous responses, and missing required proof keep it; they are uncertain, not safe to retry. The same effect key may resume only before any dispatch; an executing or uncertain write is never repeated. The agent's re-park never clears a stamp. "Posting may have failed" offers "Re-approve", which clears an uncertain stamp only after the founder checks Zernio's queue. A scheduled create is accepted only with an unambiguous `post._id` and matching target; completion additionally requires that target's matching `platformPostUrl`. The documented REST read `GET /v1/posts/{postId}` can provide typed proof. MCP `posts_get` and `posts_list` wrap a string as `result`, not a typed post; decode and validate it fail-closed and do not infer a post object. No webhook receiver.

Why this over a card: a card pauses the routine run, which `wakeRoutine` counts as active and which holds the founder's messages; the founder has already approved the exact text, time and account.

### 6. Email: approve on the page, send through the Inbox composer

An `outbound_email` item holds subject (`title`), body (`notes`) and To (`target`). The page maps it to `MailApproval` (`tool: "mail_send"`, recipient arrays, the way `mailApproval()` does for the agent's own sends) and renders `MailApprovalCard` in its edit mode; edits come back as `MailEdits` through `onAnswer` and are saved to the item with the founder's `scratchpad.update`, then Approve calls `inbox.compose.send` with `clientId = item.id` (a cuid fits `ComposeClientId`, so a double click or a retry hits the `ComposeSend` claim) and the chosen From account (a picker only with more than one Gmail account). Outcomes: `sent` or `unknown` → `scratchpad.update({ status: "done", proof: "gmail:<item.id>" })` (`unknown` is never retried by the server); `saved` (a draft was kept but not sent), `failed`, `reconnect`, `disabled` → the item stays parked and the card shows the reason. Two checks gate Approve: an unsubscribe line and a postal address (CAN-SPAM; a pure function in `apps/web/src/lib/email-compliance.ts`; "Add address" appends the founder's address through `scratchpad.update`). `ComposeEmail` is not used: its props are `seed`, `accounts`, `connectionId`, `restore`, `onClose`; it autosaves Gmail drafts and sends itself and cannot hand text back.

Why not the Inbox agent: the GTM agent could `message_bot` the Inbox agent, whose peer run has `mail_send` behind a mandatory card (`executor.ts:4277`, `:5143`), a second approval in another agent's thread that pauses that run; and B1 removes `message_bot` anyway. `compose.send` is the founder's own path, actor-scoped and idempotent. Email is sent when approved; no scheduling.

### 7. The GTM agent

- Spawn key `gtm-agent:<userId>` (`packages/contracts/src/gtm.ts`), reserved in `bots.create`, created only by `ensureGtmAgent` (`apps/api/src/gtm-agent.ts`), exposed as `gtm.agent`. ### 9. The agent arranges the page

Layout C is a guess at what every founder needs. A founder pushing X posts, one working through 40 directories and one sending design-partner emails want different pages. So the agent may arrange the page itself, using the format agent pages already have: Markdown plus fenced JSON blocks, validated on save, revision-checked, never HTML or script (`docs/agent-pages/README.md`).

- **Blocks.** Three fences beside ` ```chart `, defined in `packages/contracts/src/gtm.ts` as strict schemas (unknown keys rejected):
  - ` ```gtm-plan ` `{ group: "in_progress" | "drafts" | "done", channel?: GtmChannel[], category?: Category[], limit?: 1..50 }`: a filtered list of plan items with the same cards and buttons as layout C.
  - ` ```gtm-channels ` `{}`: the Channels table.
  - ` ```gtm-metric ` `{ label (1..40 chars), count: "done" | "in_progress" | "drafts" | "needs_you", channel?: GtmChannel, goal?: number }`: one number from `gtm.overview`, with an optional "{n} of {goal}".
- **Blocks carry a query, never data or item text.** The page renders each block from `gtm.overview` and `gtm.queue` at view time, so a block cannot show a stale or invented number or rewrite what an approval says. Numbers the overview does not know (followers, site signups) stay in prose or snapshot ` ```chart ` blocks, as today.
- **Fixed parts the agent cannot move or hide.** The header (goal, "N need you", next wakeup), the Plan | Calendar switch and the Calendar tab, the Connect Zernio card, and the full, unfiltered **Needs you** group, which in agent layout also lists every item showing "Posting may have failed" with Re-approve. These render first; the agent's page fills the rest of the Plan tab under the byline "Written by GTM agent". `gtm-plan` has no `needs_you` group, so an approval is never hidden, filtered away or shown twice. Approve, Edit, Discard and Re-approve exist only inside the app's item cards.
- **No look-alike controls.** Agent pages today allow links, images and task lists (`page-extensions.ts`), any of which could imitate an Approve button. On the GTM agent's page a save that contains a link, an image or a task list is rejected with the reason returned to the model.
- **Default.** A GTM page with no `gtm-*` block renders layout C (S5a, S5b) with the agent's page as the stats block. Once the page has a `gtm-*` block, the agent's page replaces the rest of the Plan tab below the fixed parts.
- **Where blocks are allowed.** Validation lives in `saveBotPage` (`packages/adapters/src/pages.ts`), which both `pages.save` and the page tools call. It accepts `gtm-*` fences only on the GTM agent's own page and rejects them, with the reason returned to the model, on any other bot's page. At most 12 `gtm-*` blocks per page.
- **Founder control.** The founder edits the page in the existing editor: blocks can be deleted or moved but not hand-edited, like charts. Deleting every block returns layout C. A founder who wants a different layout asks the agent in chat.
- **Instructions.** Arrange the page around this founder's goal and active channels; keep it short; update it when the plan changes; never repeat an item's text in prose. Page text is model output and may be shaped by untrusted research, which is why it cannot carry links, images, task lists or item text.
- **Why this format and not a library.** OpenUI (Thesys) and AI SDK generative UI were considered. Both use the model above: the model writes a compact spec and the app maps it to its own registered components. AI SDK generative UI renders tool results inside chat messages, not on a page that persists. OpenUI would add a dependency and a second page format next to Markdown, and its public docs do not yet state its component registration API or licence. Fences reuse the existing page store, validation, revisions and editor, with no new dependency. Revisit OpenUI Lang if other page agents need the same blocks or streaming layout matters.
- **Mobile.** The mobile agent page renders only text and charts (`apps/mobile/lib/agent-page.ts`), so S5c hides `gtm-*` fences there instead of showing raw JSON. The native screen (#301) renders layout C; agent blocks on mobile are part of that follow-up.
- **Copy.** One new string, "{n} of {goal}" on a metric; the PR quotes it.

### API

`apps/api/src/gtm.ts`, all scoped by actor:

- `gtm.agent` (idempotent create, like `legal.agent`).
- `gtm.overview`: the goal item, counts per group, the items, the routine's `nextRunAt`, the Channels rows, the Gmail accounts, whether a Zernio server is linked.
- `gtm.queue`: the app-owned Zernio REST posts endpoint, using only the configured actor/bot-scoped API key.
- `gtm.overview` selects the exact actor-owned Zernio server and calls only MCP `accounts_list`; malformed or failed account output and multiple matching servers are unavailable, not disconnected. Queue reads never call MCP `posts_list`; OAuth-only links return `api_key_required` without an empty-success queue. The later UI renders account and queue errors, API-key-required state, and incomplete queue state distinctly without exposing credentials.
- `gtmNeedsYou` in `notifications.glance` (parked gated items with `approvedAt` null).

Approve (with `updatedAt`), Edit, Discard, Mark posted and Re-approve use `scratchpad.update`/`scratchpad.remove`; email send uses `inbox.compose.send`.

### Security and tenancy

Every new query filters on `spaceId`, `userId` and `botId`; the Zernio server for page reads is selected by the actor's scope and endpoint. The open-needs-approval invariant, the race guard and the directory counts live in the store, the counts under an advisory lock; the client never passes an approval. Browser tools exist only while an approved signup is open; the Zernio posting tool only while an approved post is open, and its call must match the approved tuple and consumes it once; every other Zernio write and every generated tool is outside a closed allowlist checked before each call. The agent cannot delegate: no `message_bot`, `spawn_bot`, `handoff_to_bot` or agent-connection tools, so no other bot's browser can act for it and no owner agent can be asked to send mail. The agent has read-only access to the founder's Gmail (`mail_search`, `mail_grep`, `mail_get`) on owner-initiated runs, the same access the Legal agent has, and never `mail_send`, `mail_draft` or `mail_modify`; mail content is treated as untrusted data. Email leaves only through the founder's own `compose.send`. Proof and notes render as text; only `http(s)` proofs become links. Routine runs cannot create schedules or take over the screen. Secrets stay origin-bound.
