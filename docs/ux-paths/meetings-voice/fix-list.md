# Fix list: Granola and Wispr Flow plans and mockups

Date: 2026-10-20

This is the single, deduplicated list of changes for the Granola plan (`docs/plans/granola.md`, epic #444), the Wispr Flow plan (`docs/plans/wispr-flow.md`, epic #452) and the two mockups (`docs/granola/mockup.html`, `docs/wispr-flow/mockup.html`). Nothing is built, so every row changes a plan or a mockup, not product code.

It merges three sources: the 48 "Consolidated journey failures" in `catalog.md` (JF-1 to JF-48), the 99 findings from the static-mockup walk in `docs/ux-walker/meetings-voice/stories/*/findings.json` (25 carry a JF id; the other 74 are marked NEW or have no JF id, and every one of them is covered below), and the proposals in `docs/ux-flow/meetings-voice/` (journeys and `redundancy.md`). A source that applies to two targets appears in two rows.

## Maintainer decisions applied

These override any finding that conflicts with them.

- D1: Defer the Granola weekly memory routine (S7, #443). Close it as deferred. Meetings stay reachable through the meeting tools. Findings about S7 are resolved by deferral.
- D2: One Granola agent. The API-key connection attaches to the existing Granola agent if there is one, otherwise it creates one.
- D3: Wispr Flow is a row in the existing Voice providers list, labelled as transcribe-only. There is no separate Transcription selector. Consent is asked once for Flow at Connect, per recipient, with no global disclosure-version re-prompt. The setting ships with the Flow provider (S3a), not before.
- D4: The person who connected can delete a stored meeting together with its to-dos. Everything else is kept permanently.
- Earlier decisions still stand: Business and higher API sync, meetings private to the connecting user, follow-ups as Inbox to-dos now, and the Flow API slices #447 and #448 blocked on access.

## How to read the list

- Rows are grouped by target, so four editors can work in parallel without touching the same file: Granola plan, Wispr Flow plan, Granola mockup, Wispr mockup. Within a group, rows follow the plan's section order; rejected rows come last.
- Severity is the highest any source gave, adjusted after reading the code.
- Status: `open` means a plan editor should apply the change (rows marked "Applies D#" carry a maintainer decision into the text). `resolved-by-decision` means a decision removes the problem and no edit beyond the named row is needed. `rejected` gives the reason.
- Mockup-only rows (notes drawn as UI, touch targets, the missing unconnected state, the dark-mode disabled button, native iOS fidelity) are under the mockup targets.
- Where a finding contradicted the code, it was checked by reading the code. Results: mobile already has `TodoCard` (`apps/mobile/app/inbox.tsx:547`), so the mockup's claim that it does not is corrected (FX-60); meeting to-dos are dropped by the current query on every tab (`apps/api/src/inbox.ts:780`), so the catalog's hedge about the All tab was wrong (FX-15); "This device" on mobile voice is a checkmark `Pressable`, not a switch (`apps/mobile/app/(settings)/voice.tsx:334`), so the Wispr mockup's switch is wrong (FX-67); the mobile to-do tick already removes the row at once (`inbox.tsx:260`), so the Granola mockup's strike-through is wrong (FX-61); the mobile `TodoCard` already has `todoDueLabel` and `dueTone` (rejected in FX-62).
- Where two sources disagreed, the choice is stated in the row: meeting to-dos show on every account tab (FX-15) rather than only on All; the key hint is the muted "Business plan" on the detail page (FX-24) rather than a 401 versus 403 branch; the agent link uses the existing `IntegrationAgentSection` (FX-6) rather than auto-opening chat (rejected in FX-35).
