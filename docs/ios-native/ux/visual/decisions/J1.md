# J1: Which model-connect method leads on first run (round 3)

## Problem
Cluster C1. The Connect sheet leads with API key ("Recommended"), offers no way to get or paste a key, prefills Local server with localhost, and shows Subscription Sign in as a gray bar next to a dimmed Connect. A non-technical founder at first run does not know what an API key is, and the cheapest route for them (an existing subscription) is third. Issues: V-home-R3-1, V-home-R3-3, V-home-R3-4, V-account-R3-1, STORY-019-R3-3. Evidence: r3 screenshots of PG-A-HomeNoModel, PG-B-Models, PG-A-ThreadStates.
Acceptance: one prominent action per frame; Get a key link and Paste on the key frame; Local server Address empty with a LAN placeholder; Home card says Chief cannot reply until a model is connected; no-model thread disables the composer with a plain line and a real Connect button.

## Options considered
Weighted score out of 60 per lens (Usability / Visual / Engineering). Criterion order: acceptance, simplicity, consistency, usability, visual, effort.
| Option | Idea | U / V / E | Total |
|--------|------|-----------|-------|
| A Minimal | Keep API key first; add Get a key, Paste; fix copy | 43 / 45 / 51 | 139 |
| B Restructure | Sign in leads; Other ways expands inline | 46 / 42 / 43 | 131 |
| C Convention | Mail Add Account: Sign in leads; Other ways push to detail screens | 52 / 54 / 53 | 159 |

External judges: not run. OPENROUTER_API_KEY is not set in this environment, so second-opinion.mjs exited before any call. The earlier external-judges.json in this folder belonged to a different problem (consent) and was deleted. Brief is in proposals/J1/judge-brief.md for a later run.

## Decision
Winner: C. Sign in with Model A is the single prominent action on the first screen. API key and Local server sit in an inset list "Other ways" and push to their own screens.
Grafts from A: Get a key link and Paste button on the key screen; empty Local server field with LAN placeholder; the no-model thread line. These are already included in C's spec below.

## Why this is the best
- Against A: it leaves "API key" as the first word a new founder reads and still treats the subscription route as the third choice; usability stays the weakest score.
- Against B: inline expansion in a medium sheet pushes the footer down, and the one prominent button changes from Sign in to Connect in the same view.
- Norms: one tinted action per view; solid content, glass only on the sheet chrome; native pattern (grouped list, push, back chevron) that Mail and Settings users already know; API key stays reachable in one extra tap, so the universal path is not removed.
- Costs: sheet becomes a NavigationStack; API key users take one more tap; sign-in needs a provider that supports it (hide the lead button and promote the list if not).
