## The Simpler Version

Access model (fixes PG-40, PG-41, PG-42 together):

1. **One credential kind: a per-contact access link.** Drop the separate 15-minute single-use `link` token plus 30-day `session` token. The link is a reusable per-contact token with a lifetime (suggest 90 days, refreshed on use), valid until revoked. Reusable is what makes scanners harmless and also fixes the in-app browser cookie problem: tapping the email link again always works, on any device or browser. The cookie stays as a convenience only, not required.
2. **The landing page has an Open button.** `GET /portal/open/:token` returns a page with company name and an "Open" button; only the button (POST) sets the cookie and goes to home. Scanners and chat unfurlers issue GETs, so they cannot start a session. With a reusable link this is no longer needed to protect the token from being burned, but it still keeps scanners from creating sessions and from marking the contact "Opened" (suspected benefit). If the team wants to keep single use, this button is mandatory; with reusable links it is optional. Recommended: reusable link plus the button, because the button costs one tap and keeps "Opened" honest.
3. **Update emails: one message per recipient, not Bcc.** Send loops over recipients, each message carrying that contact's own link. Bcc is dropped, so no one is exposed and PG-42 disappears. Cost: N Gmail sends instead of 1; for a typical seed investor list (tens) this is fine (suspected; the plan lists no volume, and Gmail daily limits apply, TBD). Each email already contains the update body, so the portal link is for the history and documents.
4. **Does the update email need a link at all? Only when there is something to open.** Put the link in an email only if that contact has a shared document or earlier updates they have not seen in the email. A contact with no portal access just gets the plain email. This removes the "contact with no access" and board-recipient cases from PG-42 with one rule instead of a policy.
5. **Revoke is a flag, not a token delete.** Add `portalBlockedAt` on the contact. Revoke sets it; the request form and link exchange both refuse blocked contacts; Unblock clears it. This fixes PG-40 without deleting shares (which the founder may want to keep). The request form also stops sending links to contacts with no shares only if needed; with the flag, the form can simply send to any non-blocked contact that has a share.
6. **Failed link screen = the request form with one line.** If a token is revoked, expired, or unknown, show "This link no longer works." and the email field right there. Same text for all causes (do not leak revocation); this is PG-43 and PG-44 together.

Investor journey after the change:

1. Open the email. Subject names the company ("Example Robotics: September update"); sender is the founder's Gmail, so the name shows (suspected: needs the subject convention in the plan).
2. Read the update in the email. If they want documents or older updates, tap "View documents" (only present when there are some).
3. Tap Open on the landing page.
4. Tap Download.

Founder journey after the change:

1. Share a document: "..." menu, "Share with investors", tick, confirm. If a ticked contact has no link yet, the confirm step says "Send Priya a link too" as a pre-ticked checkbox (decision a default carries; removes the separate 301 round trip).
2. Send update: one button. Links go in per-recipient messages automatically.
3. Row shows "Invited" or "Opened Oct 4".

Step count: investor from 5 to 4 with fewer failure paths; founder share from (4 + 2 for the separate link) to 4.

## Proposed Plan Changes

1. **README "Portal security / Tokens" and `InvestorPortalToken`**: replace `kind: link|session` with one reusable per-contact token (hash only, `expiresAt`, `lastSeenAt` used for "Opened"); landing page with an Open button before the cookie is set.
2. **README "Update editor" and slice 5/6**: Send emails each recipient separately with that contact's own link (only when they have shared items); remove "Bcc from your Gmail" wording and the footer-link sentence from mockup.html line 358.
3. **README "Revocation" and PG-40**: add `Contact.portalBlockedAt`; Revoke sets it, request form and exchange both refuse it, Unblock in the contact menu.
4. **README "Portal"**: add the failed-link state (message plus inline email field) and the empty state; specify the email subject as "{Company}: {Update title}".
5. **mockup.html Investors Portal column**: replace "Send link" button and tags with one text state ("Invited", "Opened Oct 4"), actions in the "..." menu only.
6. **mockup.html update editor**: show "Share to portal" only when Gmail is not connected; delete the explanatory sentence.
7. **mockup.html Portal header**: on phone width, show the company name only; move "Signed in as ... . Sign out" to a small footer line.
8. **Share dialog (STORY-302)**: pre-tick "Send a link to people who do not have one yet".

## Clarity Issues

- **Link, access link, portal link, "Share to portal", "Send link", "Portal access"**: one concept called six ways (README "Contacts" and update editor; mockup Portal column). Pick "link" for the thing emailed and "portal" for the page; drop "access".
- **"Active"** (STORY-301 variations): undefined; replace with "Opened <date>".
- **"Share to portal" vs "Share with investors"**: two phrases for sharing; the first is for updates, the second for documents (README Update editor vs Documents). Use "Share" for both.
- **"Bcc from your Gmail"**: assumes the founder knows Bcc and why it matters; disappears with per-recipient sends.
- **"Email me a link" at /portal**: does not name the company; Tom has 6 (STORY-305). Add the company when reached from a known link; the bare /portal cannot know the company (one app-wide URL), so say "Use the email address where you get investor updates."
- **"If this address has access, a link is on its way"**: the right security choice, but add "Check spam" to the same line (PG-44).
- **Verdict on the journey as designed: convoluted** for the access model (not the screens). The portal and founder screens are close to minimal; the token model creates the blockers.
